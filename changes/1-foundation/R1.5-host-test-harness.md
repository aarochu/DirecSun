# R1.5: Host test harness and core purity check

**Status:** planned
**Files:** `firmware/components/direcsun_core/{CMakeLists.txt,include/direcsun/core/angles.hpp,src/angles.cpp}`, `firmware/test/host/{CMakeLists.txt,test_main.cpp,test_angles.cpp,test_selftest.cpp}`, `firmware/test/host/third_party/doctest/{doctest.h,LICENSE.txt}`, `tools/host-test.sh`, `tools/check-core-purity.sh`

## Spec

**Problem:** FD §19.1 makes host tests (HT-1 to HT-10) the main evidence for the control logic, and FD §7.1 principle 3 depends on a pure core that compiles on a desktop. Neither the harness nor the purity rule exists yet. Without a positive control, a harness that silently runs zero tests looks exactly like one that passes.

**Approach:**
- **Host build.** A plain CMake project at `firmware/test/host`. It compiles every source in `direcsun_core/src` together with the tests, at C++17, with `-Wall -Wextra -Werror` and AddressSanitizer plus UBSan. It is a single executable registered with CTest.
- **Test framework.** doctest v2.4.11, vendored as its single header with its MIT license. It is pinned and needs no network at build time.
- **First real core function.** `direcsun::wrap_pi(float)` maps an angle to (−π, π], as FD §11.3 requires; the estimator and controllers will use it later. Its tests cover 0, ±π, π + ε, ±3π, and large values.
- **Positive control.** A test case `selftest_must_fail` is compiled only when `-DDIRECSUN_HT_SELFTEST=ON`. `tools/host-test.sh --selftest` builds that variant and succeeds only if the test run fails.
- **`tools/host-test.sh`.** Configures, builds, and runs. It parses the doctest summary and fails if the summary is missing or reports 0 test cases.
- **`tools/check-core-purity.sh`.** Fails if any file under `direcsun_core` includes `esp_*`, `freertos/*`, `driver/*`, `hal/*`, `soc/*`, or `sdkconfig.h`. `--selftest` writes a temporary header containing `#include "esp_log.h"` into a copy of the tree and asserts that the check fails.
