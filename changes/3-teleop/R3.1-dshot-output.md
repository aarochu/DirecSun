# R3.1: DShot output

**Status:** planned
**Files:** `firmware/components/direcsun_core/{include/direcsun/core/dshot.hpp,src/dshot.cpp}`, `firmware/test/host/test_dshot.cpp`, `firmware/components/direcsun_drivers/{CMakeLists.txt,include/direcsun/drivers/dshot_rmt.hpp,src/dshot_rmt.cpp}`, `firmware/test_apps/dshot_loopback/` (its own IDF project)

## Spec

**Problem:** The wheel is the only actuator, and the ESC accepts only DShot. Nothing in the firmware can produce a frame yet. A wrong CRC or bit timing makes the ESC ignore frames, which looks exactly like a dead ESC, so the encoder needs an instrument that proves what actually leaves the pin.

**Approach:**
- **Core (pure, FD §10.6).**
  - `uint16_t dshot_frame(uint16_t value12)`: builds the 16-bit frame `(value12 << 4) | crc`, with `crc = (v ^ (v >> 4) ^ (v >> 8)) & 0xF` over the 12-bit value. The telemetry bit is always 0.
  - `uint16_t dshot_value_for_throttle(int request)`: maps a controller request to a legal 11-bit value. 0 stays 0; 1 to 47 become 0, because flight code never sends commands (FD §21 rule 1); 48 to 2047 pass through; anything above 2047 clamps to 2047; negative values become 0.
- **Driver (`direcsun_drivers`).**
  - An RMT TX channel on GPIO7 (XIAO D8) with a 40 MHz resolution, using the built-in bytes encoder, MSB first, 2 bytes per frame.
  - Symbols for DShot150 (the default, `dshot_rate` = 150): bit 267 ticks, '1' = 200 high + 67 low, '0' = 100 high + 167 low. DShot300 halves those tick counts.
  - `dshot_rmt_init(gpio, rate)` and `dshot_rmt_send(uint16_t value11)`. The send is non-blocking (`rmt_transmit` with queue depth 2). It asserts that the value is 0 or between 48 and 2047, so a command value is a crash in testing rather than a silent ESC setting change.
  - `dshot_zero_sender_start()` / `stop()`: an `esp_timer` sends DShot 0 every 2 ms from boot until the control task (R3.4) takes over the output. The handover never leaves a gap longer than 2 ms.
- **`firmware/test_apps/dshot_loopback/`.** Its own IDF project, sharing the firmware's `sdkconfig.defaults`. It needs a jumper from D8 (GPIO7) to D3 (GPIO4).
  - An RMT RX channel on GPIO4 captures the frames, decodes the pulse widths back to 16 bits, and checks the CRC.
  - It transmits the four HT-1 vectors at both rates and prints PASS or FAIL for each.
  - It also transmits one frame with a deliberately wrong CRC, built through a test-only raw path, and expects the decoder to report a CRC error. That is the positive control.
  - Finally it streams DShot 0 every 2 ms for the oscilloscope and ESC checks.

## Tests
- [ ] HT-1 host test passes: the four FD §10.6 vectors (`0x0000`, `0x0606`, `0x82C6`, `0xFFEE`); every request from 1 to 47 maps to 0; 2048 and 65535 clamp to 2047; -1 maps to 0. Run through `tools/host-test.sh`, which also proves the run executed more cases than before.
- [ ] Loopback self-test on the XIAO, with the D8-to-D3 jumper: all 8 vector-and-rate pairs PASS, and the corrupted-CRC frame is reported as a CRC error. If the decoder accepted everything, the corrupted frame would show PASS.
- [ ] Oscilloscope on D8 at DShot150, an independent check of the timing: bit period 6.67 µs ±2%, '1' high 5.0 µs, '0' high 2.5 µs, one frame every 2.0 ms. Julian reports the readings (or a photo), recorded in Notes.
- [ ] ESC accepts the stream. With Julian present, and his go for powering the ESC from the bench supply: DShot 0 only, so the motor cannot turn. The ESC plays its arming tones (low then high, TD §6.3). If the frames were malformed, the ESC would stay silent or beep its no-signal pattern.
