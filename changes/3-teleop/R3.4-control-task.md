# R3.4: Control task, boot sequence, estimator subset

**Status:** planned
**Files:** `firmware/main/{app_main.cpp,control_task.hpp,control_task.cpp,shared.hpp,shared.cpp,CMakeLists.txt}`, `firmware/components/direcsun_core/{include/direcsun/core/estimator.hpp,src/estimator.cpp,include/direcsun/core/snapshot.hpp}`, `firmware/test/host/test_estimator.cpp`

## Spec

**Problem:** The drivers from R3.1 to R3.3 and the logic from R3.6 need one owner that runs them at 500 Hz in the right order, never waits on the network, and fails to zero throttle (FD §7.1). The boot path must put DShot 0 on the wire first (FD §8). A hung control loop must reset the board quickly, even though the system task watchdog is 5 s.

**Approach:**
- **Boot sequence (FD §8.1).**
  1. Start the DShot zero sender.
  2. Initialise NVS, load parameters (R3.6), bring up the I2C bus and probe sensors (R3.2), initialise the ADC and Hall (R3.3).
  3. Wait until at least 1 s of DShot 0 has been sent.
  4. Start the control task, which takes over the DShot output from the zero sender with no gap.
  5. Start comms (R3.5).

  Wi-Fi never delays control.
- **Tick source.** A `gptimer` alarm at 500 Hz. The ISR sends `vTaskNotifyGiveFromISR` to the control task, which is pinned to core 1 at priority `configMAX_PRIORITIES - 2`.
- **Tick body (FD §9.1).**
  1. IMU burst every tick; magnetometer poll on even ticks; ADC reads spread over ticks 0, 3, and 6 of every 10; drain the Hall ring.
  2. Estimator update.
  3. Mode and interlock step (R3.6), then the controller output.
  4. Send one DShot frame.
  5. On every 10th tick, publish a telemetry snapshot.
  6. Record `loop_us`, the longest tick in the last 20 ms.
- **Barometer off the control path (from R3.2).** `baro_read()` can block about 0.3 s on a bus error, so the BMP280 is read at 1 Hz by a low-priority task on core 0, not on a spare control tick as FD §10.3 says. That task shares the bus through i2cdev's port lock, and the control task's own IMU and magnetometer reads use the 2 ms-timeout direct path from R3.2. The FD §10.3 text is updated to match, with a §23 row.
- **Shared state (FD §7.4).**
  - The command queue (depth 16) and the event/ack queue (depth 16) are FreeRTOS queues, both used with timeout 0.
  - `estop_requested` and `last_heartbeat_us` are atomics.
  - The telemetry snapshot is a double buffer with a sequence counter (seqlock). Control writes the inactive buffer and flips; comms copies and retries if the counter moved. Control never waits on comms.
- **Control-stall watchdog [D].** The system TWDT has one global timeout, kept at 5 s for the idle tasks. A per-task 100 ms limit therefore lives in the gptimer ISR. It counts alarms since the control task last completed a tick. At 25 missed ticks (50 ms) the control task's own `CONTROL_STALL` soft interlock trips, if the task is still alive (R3.6). At 50 missed ticks (100 ms) the ISR calls `esp_system_abort("CONTROL_STALL")`, the board resets, and the boot path is sending DShot 0 again within milliseconds (FD §14.5).
- **Estimator subset** (pure core, FD §11.1, §11.5):
  - Box rate ω̂ = s_gyro · (g_z − b_z).
  - Bias b_z is a 5 s exponential average, updated only in SAFE when the box is still (|g_z − b_z| < 2 deg/s, |a| within 0.05 g of 1 g, wheel below 200 rpm or not reported).
  - Tilt from the 20 ms averaged accelerometer.
  - vbat from the 1 s average.

  Heading and sun come in Set 5.

## Tests
- [x] HT-3 subset on the host:
  - The bias converges to a constant offset within 5τ while still.
  - The bias freezes while |rate| > 2 deg/s, and outside SAFE.
  - Tilt reads 0 deg at 1 g on z and 30 deg at the matching vector.
  - Positive control: feeding a spinning-box trace in SAFE (as after an e-stop) leaves the bias unchanged. An estimator without the stillness gate fails this.
- [ ] Tick jitter on the XIAO (BC-3): over 10 s, 5000 ticks ±1, a tick period of 2000 µs with p99 deviation under 50 µs, and no missed ticks. Logged from `esp_timer_get_time()` at tick start.
- [ ] Timing budget: `loop_us` max under 1000 µs over 10 min with every sensor read and Wi-Fi connected (FD F-4 "done when").
- [ ] DShot never gaps. The oscilloscope on D8 shows a frame every 2.0 ms, both across the boot handover from zero sender to control task and during 60 s of running.
- [ ] Control-stall watchdog (BC-5), with a positive control. A test hook compiled only in a bench build blocks the control task for 200 ms. The board resets within 150 ms of the block starting. The reset reason is logged on the next boot. The oscilloscope shows DShot frames again within 300 ms of the reset, which is inside the ESC's own 0.3 s signal-loss cut (TD §5.2). The original 50 ms figure is below the ROM, bootloader, and app start-up time; changed 2026-10-10. If the watchdog were missing, the board would keep running.

## Notes / log
- 2026-10-10: Built on `feat/set3/R3.4-control-task` (stacked on the R3.1 to R3.3 branches): e2d66db (core `estimator` and `snapshot`, HT-3, the `no_still_gate` mutant) and 1128a41 (`main/` app, control task, shared state, services, NVS store, Kconfig, `sdkconfig.bench`, FD §10.3 and V-37).
  - Boot sequence:
    1. NVS and parameters are loaded, then DShot 0 starts at the stored rate.
    2. Sensors and the ADC come up.
    3. A boot window of at least 1 s and 500 frames primes the battery average and seeds the gyro bias.
    4. The barometer, persistence, and status tasks start on core 0, then the control task on core 1. Its first tick takes the output over from the zero sender with no gap.
  - Interface for R3.5 (`main/shared.hpp`): `shared_push_command` (false means reply "busy"; pings go through it too), `shared_request_estop`, `shared_pop_outbound` (an ack to one client, or a broadcast event), and `telemetry().read()`.
  - Results:
    - HT-3 subset passes, with 80/80 host cases. The `no_still_gate`, `no_latch`, and `no_bypass_clamp` mutants are all caught by `--selftest`.
    - Purity: 17 files.
    - The flight build has 0 warnings; a planted unused variable warned, so that zero is real. The image is 0x478b0 B, with 81% of the partition free.
    - The stall hook is absent from the flight binary by `nm` and `strings` (0 symbols, 0 strings) and present in the bench build (1 and 2). The flight binary's `CONTROL_STALL` strings prove both tools can see its contents.
  - Decisions [D]:
    - Parameters load before DShot starts, so the rate never switches mid-stream.
    - The gptimer ISR is not cache-safe, which is acceptable because flash writes happen only in SAFE.
    - The gyro bias is seeded during the boot window, because the MPU-6050 offset can exceed the 2 deg/s still gate.
    - Heading is gyro-only for now.
    - Tilt reads 90 deg when |a| is below 0.2 g, so a falling box trips TILT.
  - Pending hardware (procedure):
    - Flight build: `tools/idf.sh -p <port> flash monitor`. Expect `status: ticks 500`, `missed 0`, `p99_dev_us` under 50, `loop_us_max` under 1000, and `dshot sent` rising by about 500/s with 0 dropped.
    - Bench build: `tools/idf.sh -B build-bench -D SDKCONFIG=build-bench/sdkconfig -D DIRECSUN_EXTRA_DEFAULTS=sdkconfig.bench -p <port> build flash monitor`, for the stall watchdog.
  - Known limit (FD §11.1): a bias seeded while the box turns steadily under 25 deg/s at boot is never corrected.
