## Spec

**Problem:** (UI paths and line numbers below are as of c4e3b0c; PR #28 has since moved the operator client to `frontend/ground-station/`.) The main UI is the operator client at `frontend/draft/` on `main` (c4e3b0c; box controls from PR #10, `zero_heading` from PR #13, merged 2026-10-11 00:34 UTC). It runs the judge sequence itself. The firmware at the top of the stack is `feat/set4/R4.3-hold-and-slew` (5cb6263). An audit on 2026-10-10 compared them message by message. It drove the UI, built from `main`, in headless Chrome against two boxes: the R4.3 mock box, and a host build of the real R4.3 core (`parse_inbound`, `Supervisor`, `CascadeController`, `Estimator`, the encoders) closed around `plant_sim.hpp` and put behind a WebSocket. That bridge replicated the comms routing of `ws_server.cpp` and `comms.cpp`. The result: the message set already matches, but one ordering defect breaks the demo, and the mock hides it.

What the UI sends and expects (from the source at c4e3b0c):
- `deviceLink.ts:381`: every command is `{"v":1,"type":"cmd","seq",cmd,...fields}`, with one `seq` counter shared with pings (`:359-362`, wrapping below 2^32).
- `deviceLink.ts:401-415`: from its first command, a ping `{"v":1,"type":"ping","seq","t_client_ms"}` every 200 ms. `t_client_ms` is `performance.now()` with three decimals, so it is fractional. Pings never stop while the socket is open.
- `deviceLink.ts:156`, `:374-382`: every command, `estop` included, must be acked by `seq` within 1000 ms, or it fails with `TIMEOUT`.
- It reads `ack.{seq,ok,reason}` (`:385-399`), `pong.ping_seq` (`:417-423`), and `event` with `event` `mode` or `notice` plus `mode`, `cause`, `name`, `detail` (`:340-353`). Control frames must carry `v` 1 (`:332`). From tlm it reads `mode`, `psi_deg` (required), `psi_ref_deg`, `rate_dps`, `wheel_rpm`, `wheel_ref_rpm`, `throttle_band`, `flags`, `vbat`, `t_ms`, `seq` (`:93-120`).
- `deviceOperator.ts:96-134`: `arm`, `disarm`, and `estop` (button, or the space bar while armed, `DeviceControls.tsx:43-59`). After the arm ack it controls until a tlm shows SAFE (`:239-248`). A SAFE event whose cause is not `disarm` shows "THE BOX WENT SAFE: <cause>" (`:250-254`).
- `deviceOperator.ts:136-155`, the turn: `zero_heading`, then `mode SLEW psi_ref_deg ±90`. It waits up to 10 s for an event `mode READY` with cause `slew_complete`, and fails on `SLEW_TIMEOUT`, any other READY cause, or a mode other than SLEW or READY (`:170-187`). A READY tlm without that event fails after 1 s. Then it holds 1 s, failing on **any tlm frame whose mode is not READY** (`:147`), then sends `mode SLEW psi_ref_deg 0` and waits the same way.
- `deviceOperator.ts:157-168`, Stop turn: it cancels the turn locally and sends `mode READY` only if the newest tlm already says SLEW.

Confirmed, with evidence, and needing no change:
- **Parsing.** The schema (R4.3 and `main`) and the real `parse_inbound` accept every frame the UI sent: 792 of 792 captured frames (737 pings, 55 commands). Planted bad frames (−180, an extra field, a missing `t_client_ms`, seq 2^32, v 2) were all rejected, so the probe can see a rejection.
- **Sign and wrap.** Wire +90 decodes to internal −90, so "Rotate right" turns the plant clockwise and tlm reads +89.08. Wire −90 decodes to +90. A wire 0 is a valid return target.
- **Acks.** Every command was acked exactly once within 25 ms (98 commands; localhost plus the 20 ms comms period). All were `ok` except a deliberate re-arm inside the ramp-down.
- **Events.** `spinup_complete`, `slew_complete`, and `SLEW_TIMEOUT` (exactly 6.0 s after entry at 30 mN·m) reach the operator. The UI reports them as it intends: "TURN COMPLETE", "THE BOX TIMED OUT THE SLEW".
- **Stop and heartbeat.** `mode READY` during SLEW ends it with cause `mode`, and the box stops on the rate loop ("HOLDING WHERE THE BOX IS" matches FD §12.4: rate, not heading). Losing the UI's socket gives `HEARTBEAT_LOST` 1008 ms after its last ping.
- **Watch-only client.** It receives only tlm (728 frames, no events) until it speaks. Its e-stop is accepted from a non-controlling client and stops the box.
- **Timing.** The UI's 10 s slew wait and 1 s hold fit the 6 s timeout and the completion rule: slews complete 2.97 s after entry at the design gains.
- **No missing command.** `zero_heading` exists on every layer with the meaning PR #13 assumes (SAFE and READY only; SLEW targets are relative to it). The device controls send no `reset` and no `respin`.

Gaps:

1. **A stale tlm after `slew_complete` aborts the turn (breaks the demo).** `control_task.cpp:385` writes the snapshot only when `tick % 10 == 0`, and *after* posting that tick's acks and events (`:365-376`). The comms task wakes on its own 20 ms FreeRTOS period (`comms.cpp:16`, `:36`). It pops every queued ack and event, then publishes the newest snapshot (`:39-58`). The flush sends the queue first and the tlm last (`ws_server.cpp:166-194`). An event posted in a tick after the newest snapshot therefore goes out followed by a tlm from *before* the transition. After `slew_complete`, that tlm still says SLEW, and the UI's hold check (`deviceOperator.ts:147`) ends the turn with "TURN STOPPED: THE BOX LEFT READY (SLEW)": the box stays at ±90 and never returns. The exposure per event is about (comms phase in ticks after a snapshot)/10, and the phase is fixed for a boot.
   - **Reproduction.** I modelled the pipeline in the host harness and ran the real UI against it. At comms phases 3, 6, and 9, 8 of 12 turns failed; at phase 0, 0 of 2. The captured order was: event READY/`slew_complete` at box time 10656 ms, then a tlm at 10640 ms with mode SLEW.
   - **Fix tested.** The rule in Approach 1 gave 0 stale frames after 60 mode events across all ten phases (16 of 60 without it) and 4 of 4 completed UI turns at phase 9.
   - **Not visible elsewhere.** Neither the mock box nor the UI's own e2e fake box can produce this: both always send a tlm that is current after an event.
   - **Hardware.** This is inferred from the code and not yet observed on the real box. No WebSocket capture of the real box exists.
2. **Stop turn race (UI side).** If Stop is pressed after `mode SLEW` has gone out but before a tlm shows SLEW, the UI cancels locally, sends nothing, and reports "TURN STOPPED: HOLDING WHERE THE BOX IS". The box then completes the full 90° slew. I reproduced this on both boxes by holding box-to-UI frames for 150 ms. The window is one network and comms delay, about 20 to 60 ms. The fix is Aaron's: send `mode READY` whenever a turn has a SLEW in flight. The firmware's part is to guarantee that `mode READY` in READY is a harmless `ok`. It already is, but no test pins it as a contract.
3. **The mock teaches behaviour the firmware does not have.** Aaron tests against the mock, so a pass there overstates readiness. Same commands and states, different answers:

   | Command and state | Firmware | Mock |
   | --- | --- | --- |
   | `arm` within 5 s of an e-stop or disarm | `ramp-down in progress` | accepts and spins up |
   | `disarm` in SAFE | `not armed` | `already SAFE` |
   | `mode READY` in SAFE | `not armed` | `not allowed in SAFE` |
   | `arm` in SPINUP | `not in SAFE` | `not allowed in SPINUP` |
   | `mode READY` in SPINUP | `wheel not at bias` | `not allowed in SPINUP` |
   | `mode DETUMBLE` | `not implemented` | accepts |
   | `mode SUN_POINT` | `not implemented` | `sun not valid` |
   | `respin` | `not implemented` | accepts |

   Other differences:
   - The mock has none of the arm guards `box not still`, `battery low`, or `latched fault: <NAME>`.
   - It reaches READY 2 s after arm; the firmware takes about 6.2 s (Ω_ref ramps at 400 rpm/s, then a 0.5 s dwell).
   - It sets `MOMENTUM_OK` or `MOMENTUM_NEAR_LIMIT` in SAFE and SPINUP, where the firmware sets neither.
   - It defaults to a characterised box; the firmware defaults to none (`ff_count` 0, `rate_gain_scale` 0.2).
4. **The contract documents are stale.** FD §17 still describes PR #1's read-only link and PR #10's flow (capture `psi_deg`, SLEW to start ± 90, SLEW back to the captured start), not PR #13's (zero, then ±90, then 0). FD §15.2, FD §14.4, the schema's `event` description, and `protocol/README.md` say the UI never sends and counts every non-tlm frame as ignored. `_set.md` open question 2 says the UI sends no ping. None of this is true at c4e3b0c.
5. **UI defects found on the way (Aaron's code; issues, not firmware work).**
   - Disconnecting an armed box swaps straight to the simulation with enabled Rotate buttons. The operator's "LINK CLOSED" warning is never shown, because the device controls unmount (`GroundStationPage.tsx:34-49`).
   - The operator's own e-stop is reported in red as "THE BOX WENT SAFE: ESTOP" (`deviceOperator.ts:250-254`).
   - "ANOTHER CLIENT IS CONTROLLING THE BOX" flashes for 25 to 55 ms after every e-stop. `DeviceControls` reads the mode from 50 ms-throttled telemetry (`deviceLink.ts:442-448`), while the operator drops control on the first SAFE frame.
   - `HEADING_GYRO` shows as a permanent warning chip (`deviceLink.ts:35-38`).
   - TARGET reads the moving profile reference in SLEW and falls back to the heading in READY, so it does not show +90 during the hold. The UI's own fake box sends the final target instead (`e2e/box-control.spec.ts:36`).
   - The ping timer is a page `setInterval`. Chrome throttles that to about 1 Hz in a hidden tab, which would race the 1 s heartbeat. This is unverified: headless Chrome does not throttle.

**Approach:**

1. **Ordering guarantee (the only firmware behaviour change).**
   - **Rule.** The first tlm a client receives after an `ack` or `event` reflects the control tick that produced it, or a later one.
   - **Core helper.** `snapshot.hpp` gains `constexpr uint32_t kTicksPerSnapshot = 10;` (moved from `control_task.cpp`) and `constexpr bool snapshot_due(uint32_t tick, std::size_t outbound_count)`. It returns `tick % kTicksPerSnapshot == 0 || outbound_count > 0`.
   - **Control task.** Step 5 of `control_task.cpp` computes `outbound = out.acks.count + out.events.count`, writes the snapshot when `snapshot_due(tick, outbound)`, and only then posts the acks and events. Comms always pops a posted item before it reads the snapshot (`comms.cpp:39` before `:53`), so any event it can see already has a snapshot at least that new, and the flush sends that snapshot after the event.
   - **Effects.** The tlm rate stays 50 Hz, because comms publishes at most one snapshot per period. Commands are rare, so the extra writes cost about 7 µs each on those ticks (FD §9.2). `t_ms` stays monotonic.
   - **Not changed.** An event's `t_ms` is still comms' encode time, so clients must order events against tlm by socket order, not by `t_ms`. FD §15.3 says so.
   - **Rejected alternatives.** Sending tlm before the queue in each flush also hides gap 1, but gives no invariant. Posting acks and events only on snapshot ticks needs a multi-tick outbound buffer and delays acks. Leaving it to the UI keeps a firmware ordering that any client would trip over.
2. **`mode READY` contract.** It is accepted in READY with `ok`, no event, and no change to mode, references, or flags. In HOLD, SLEW, and MANUAL it goes to READY with cause `mode`. Refusals: `not armed` in SAFE, `wheel not at bias` in SPINUP. This is today's behaviour, now pinned by HT-13, so the UI may send `mode READY` at any time a turn has a SLEW in flight.
3. **HT-13, `test_ui_contract.cpp`.** It uses `box_rig.hpp`, the real core, and the plant. Cases:
   - **(a) UI frames.** The exact UI strings parse to the expected kind, seq, target, and internal `psi_ref_deg`. These are `{"v":1,"type":"ping","seq":1,"t_client_ms":473.6}`, `arm`, `zero_heading`, `mode SLEW` 90, −90 and 0, `mode READY`, and `estop`. The ping's pong echoes `t_client_ms` 473.6 and `ping_seq` 1.
   - **(b) Judge sequence as the UI runs it.** The operator client pings every 100 ticks, with characterised params, `rate_gain_scale` 1, friction 0, 1, and 3 mN·m, and both directions. The steps: `arm`, then READY by `spinup_complete`, then the pin is released, then `zero_heading`, then SLEW ±90. That ends in `slew_complete` in under 3.5 s, after which comes 500 ticks of READY with no mode event, then SLEW 0, then `slew_complete`. Finally `estop` from a second client, which is acked to that client, followed by SAFE/`ESTOP`. The plant's true heading change is −90 ± 3° for wire +90 and +90 ± 3° for wire −90, so a lost wire sign fails. Every ack is `ok` and is posted in the tick its command was drained.
   - **(c) Pipeline invariant.** A comms model wakes every 10 ticks at each phase 0 to 9. It pops everything posted so far, then takes the newest snapshot written under `snapshot_due`, with the snapshot written before posting, as in step 5. It runs (b). For every mode event, the next snapshot sent has the event's mode. For every ack, the snapshot sent after it is from the ack's tick or later.
   - **(d) `mode READY` in each state.** As in Approach 2.
   - **(e) Stop right after SLEW.** SLEW ±90, then `mode READY` on the next tick: both `ok`, events SLEW/`mode` then READY/`mode`, and the box stops within 10° of where it started.

## Open questions
1. **A host-built "core box" and a parity check.** The audit's strongest evidence came from running the real core behind a WebSocket. A permanent `tools/core-box` would make the mock's drift (gap 3) a test failure instead of an audit finding. It is a second host target in `firmware/test/host/CMakeLists.txt`, with a Python bridge sharing `mock-box.py`'s server code, plus `tools/check-mock-parity.sh` that runs one scripted conversation against both and diffs the (ack ok, reason) and (event mode, cause) sequences, ignoring timing. Recommendation: yes, as a follow-up feature after the demo, not in R4.1, so that R4.1 stays small enough to land first.
2. **Demo preconditions the UI cannot see.**
   - **The risk.** A box without `ff_table` refuses SLEW with `wheel loop not available`. In the host sim it also never leaves SPINUP, because it falls back to open-loop throttle. At the post-reset `rate_gain_scale` 0.2 and 3 mN·m, the sim's slews completed at 5.81 s and 5.90 s, against the 6.0 s timeout.
   - **Why the UI cannot see it.** The `PARAMS_RESET` notice is posted on the first tick after boot, when no client has spoken, so it reaches no one: an unrelated defect from R3.x.
   - **Recommendation:** yes, two additive v1 flags, `FF_TABLE_MISSING` (Hall installed and `ff_count` 0) and `RATE_GAIN_REDUCED` (`rate_gain_scale` < 1), set in every mode. The UI already shows unknown flags as warning chips, so they appear with no UI change. They need fixtures, a README row, and the mock. Without them, the pre-demo checklist must check `wheel_ref_rpm` > 0 in READY and re-send `rate_gain_scale` 1 from the bench console.
