# R4.6: Status flags the UI cannot otherwise see, and refusal strings for DETUMBLE and SUN_POINT

**Status:** implemented on a draft branch, awaiting Julian's approval of the spec (issue 80 P1.1 and P1.2; contract issues 62 and 59)
**Files:** `protocol/schema-v1.json`, `protocol/README.md` (Changes), `protocol/examples/valid/tlm-status-flags.json`, `firmware/components/direcsun_core/{include/direcsun/core/modes.hpp,src/modes.cpp}`, `firmware/test/host/test_modes.cpp`, `firmware/test/host/test_protocol.cpp`, `firmware/test/host/CMakeLists.txt`, `tools/host-test.sh`, `tools/mock-box.py`, `docs/firmware-design.md` (§13.1, §15.2, §15.3, §23), `docs/technical-design.md` (§6.6 refusal strings)

## Spec

**Problem.** Three things the operator needs are invisible to the ground station until it is too late.
1. A box without an `ff_table` (or with no Hall) refuses `mode HOLD`, `mode SLEW` and `wheel_step` with `wheel loop not available`. The UI learns this only after the operator presses Rotate.
2. The rate loop runs at `rate_gain_scale` (default 0.2) after every boot. The judge sequence needs 1.
3. The `PARAMS_RESET` notice is posted on the first tick after boot, before any client has spoken, and `event` frames go only to clients that have sent a message, so nobody ever receives it.

And two refusals have no string in FD §13.1: `mode DETUMBLE` (now implemented, R4.4) and `mode SUN_POINT` (R5.4).

**Approach (all additive, schema stays v1).**

1. Three new `tlm.flags` names, set by the supervisor, in every mode including `SAFE`:
   - `FF_TABLE_MISSING`: `hall_installed` and `ff_count` is not `kFfPoints` (the Hall is fitted and the T-5 table is not set). It is exactly "the Hall is fitted and `wheel_loop_available()` is false". It is not set while the Hall is bypassed, because `HALL_BYPASS` already says there is no wheel loop.
   - `RATE_GAIN_REDUCED`: `rate_gain_scale` below 1.
   - `PARAMS_RESET`: the stored parameters were missing, of another version, or invalid, and the defaults are running. The flag is set from boot until the first successful `set_params` (any accepted update, which persists the parameters), then cleared. This is the issue's second option ("carry it as a flag until the next successful `set_params`"). It needs no per-client state, reaches a client that connects at any time, and survives a client reconnect. The one-shot `notice` event stays as it is (it still reaches the serial log and any client that spoke in time), so nothing that reads it breaks.
2. Refusals, in this check order:
   - `mode DETUMBLE` from any mode but `READY`: `not in READY` (already so, R4.4). From `READY` without the closed wheel loop: `wheel loop not available` (already so).
   - `mode SUN_POINT` from any mode but `READY`: `not in READY`. From `READY` while no valid sun angle exists: **`sun not valid`**. The firmware has no sun-angle input until R5.4, so today every `READY` request gets `sun not valid`, which is true (`sun_valid` is false in every `tlm`). The final `not implemented` is reached only when the sun is valid and the mode is still unbuilt, which R5.4 replaces with the real entry. **Proposal for Julian to confirm**: the strings are `not in READY` and `sun not valid`, as issue 59 proposes.
3. TD §6.6's magnetometer guard on Hold and Slew (the other half of issue 59) is already fixed on this stack: a search for the old wording (`magnetometer present`, `blocks only Hold`) finds nothing in `docs/technical-design.md`. TD §6.6 gains the two refusal strings in its transition table instead.

**Not in this feature.** The UI greys out Rotate on `FF_TABLE_MISSING` (Aaron's side, `frontend/ground-station`, after this merges). No change to the arm guards, the interlocks, or any limit.

## Tests

- [x] Host (`test_status_flags.cpp`), flags: with the defaults (Hall fitted, `ff_count` 0, `rate_gain_scale` 0.2), `FF_TABLE_MISSING` and `RATE_GAIN_REDUCED` are in `out.flags` in SAFE, SPINUP, READY, and MANUAL; with the cascade parameters (table set, scale 1) neither is set; with the Hall bypassed and no table, `FF_TABLE_MISSING` is not set and `HALL_BYPASS` is; `set_params` `rate_gain_scale` 1 clears `RATE_GAIN_REDUCED` on the next tick, and a table clears `FF_TABLE_MISSING`.
- [x] Host, `PARAMS_RESET`: a supervisor built with `params_were_reset` carries the flag from the first tick, still posts the notice once, keeps the flag across 100 ticks and across arm and disarm, and drops it on the tick after the first accepted `set_params`. A refused `set_params` (an invalid key, or in an armed mode) leaves it set. A supervisor built from loaded, valid parameters never sets it.
  - Positive control: mutant `params_reset_sticky` (the flag is never cleared) is caught by this test in `tools/host-test.sh --selftest`.
- [x] Host, refusals: `mode DETUMBLE` and `mode SUN_POINT` from SAFE, SPINUP, MANUAL, HOLD and SLEW answer `not in READY`; `mode SUN_POINT` from READY answers `sun not valid`; `mode DETUMBLE` from READY without the table answers `wheel loop not available`; none of these changes the mode or posts an event.
- [x] Host (`test_protocol.cpp`): a `tlm` with the three flags encodes them by name, in bit order, and validates against `protocol/schema-v1.json` (HT-9 picks up the new fixture).
- [x] `tools/check-schema.py`, `tools/check-protocol.sh`, and `tools/check-link.sh` pass with `protocol/examples/valid/tlm-status-flags.json`; an invalid fixture with a misspelt flag (`FF_TABLE_MISSING_`) is rejected.
- [x] `tools/mock-box.py --selftest` passes with the same three flags and the same refusal strings; falsifier: run against the mock before this change, the new cases fail.
- [x] `tools/host-test.sh --selftest` and `tools/check-all.sh` pass (9 of 9).
- [ ] `tools/check-all.sh --firmware` (the firmware build): not run, ESP-IDF is not installed in the session that wrote this. CI runs it.
- [ ] Hardware, with Julian: flash, connect, and read `tlm.flags` on the real box in SAFE: `PARAMS_RESET` after a parameter reset, `FF_TABLE_MISSING` before T-5, `RATE_GAIN_REDUCED` at the default. No motor is turned for this.
