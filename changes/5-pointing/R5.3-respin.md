# R5.3: respin (lock-pin desaturation and alternate wheel start speeds)

**Status:** proposed, awaiting Julian's approval (issue 80 P1.5, issue 61). No code until approved: this spins the wheel to a new speed.
**Files:** `firmware/components/direcsun_core/src/modes.cpp` (`CommandKind::Respin`), `firmware/test/host/{test_respin.cpp,CMakeLists.txt}`, `tools/{host-test.sh,mock-box.py}`, `docs/firmware-design.md` (§13.1, §13.4), `protocol/README.md` only if a refusal string is new, `frontend/ground-station/src/hardware/modes.ts` (a later UI PR)

## Spec

**Problem.** `respin` is in schema v1 and FD §13.4 (the lock pin is the desaturation actuator, TD §3.6): from READY, with the box held, return the wheel to a start speed, so the operator can pull the pin and continue. The firmware answers `not implemented` (`modes.cpp`, `CommandKind::Respin`).

**Approach.** (FD §13.4's flow, written as rules.)
1. `{"cmd":"respin"}` or `{"cmd":"respin","wheel_rpm":n}`, from the controlling client only (`not controlling client`).
2. Guards, in this order, each with an exact string: `not in READY` (from any other mode, including SAFE); `wheel loop not available` (no Hall or no table: the SPINUP target is a closed-loop speed); `box not still` (box rate at or above 5 deg/s, the arm threshold); `invalid setpoint` (`wheel_rpm` not finite, or outside [Ω_low + 200, Ω_cap − 200], FD §13.4; the default when absent is `omega_bias_rpm`). The battery and latch checks of `arm` are not repeated: a latched fault has already put the box in SAFE, and the battery interlock still runs in SPINUP.
3. On success: `spinup_target_rpm_` is the requested speed, the mode becomes SPINUP with a `mode` event of cause `respin`, and the existing SPINUP rules apply unchanged (ω_ref ramps from the wheel's speed at 400 rpm/s, READY after 0.5 s within 5 % of the target). The READY it reaches holds the new speed as its bias until the next `arm`.
4. The heartbeat, interlocks and caps are unchanged. The ramp-down on `disarm` or `estop` is unchanged.

**Open for Julian (before approval):** whether `respin` should also be allowed from SPINUP to change the target mid-ramp. This spec says no (`not in READY`), which is the FD §13.4 flow.

## Tests

- [ ] Host (`test_respin.cpp`): each refusal gives its exact string with nothing changed and no event: SAFE, SPINUP, MANUAL, HOLD (`not in READY`); a second client (`not controlling client`); no table (`wheel loop not available`); rate 5 deg/s and above (`box not still`); `wheel_rpm` NaN, Ω_low + 199, Ω_cap − 199 (`invalid setpoint`).
- [ ] Host: a respin to 1000 and to 3800 from READY enters SPINUP with a `respin` event, ω_ref ramps at 400 rpm/s, READY follows 0.5 s after the wheel is within 5 % (in the plant sim), and the READY bias is the new speed; with no `wheel_rpm` it returns to `omega_bias_rpm`. The limits Ω_low + 200 and Ω_cap − 200 are accepted.
  - Positive control: mutant `respin_no_still_gate` (the `box not still` check removed) is caught by the 5 deg/s case.
- [ ] Host: `estop`, `disarm`, and a lost heartbeat during the respin SPINUP give SAFE with the ramp-down.
- [ ] `tools/mock-box.py --selftest`: the same guards and the same event; falsifier: the previous mock answers `not implemented`.
- [ ] `tools/host-test.sh --selftest`, `tools/check-all.sh`, and `tools/check-all.sh --firmware` pass.
- [ ] Hardware, with Julian's explicit go before each motor-capable step: respin to 1000 and to 3800 rpm with the box pinned; READY follows; the pin comes out; `MOMENTUM_NEAR_LIMIT` clears.
