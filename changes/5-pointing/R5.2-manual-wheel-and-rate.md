# R5.2: MANUAL wheel and rate inputs

**Status:** proposed, awaiting Julian's approval (issue 80 P1.5, supersedes issue 25). No code until approved: this changes what the motor does.
**Files:** `firmware/components/direcsun_core/{include/direcsun/core/control.hpp,src/control.cpp}`, `firmware/main/control_task.cpp` (one line), `firmware/test/host/{test_controllers.cpp,test_closed_loop.cpp,CMakeLists.txt}`, `tools/{host-test.sh,mock-box.py}`, `docs/firmware-design.md` (§12.1, §13.5), `frontend/ground-station/src/hardware/modes.ts` (a later one-line UI PR, not this feature)

## Spec

**Problem.** FD §13.5 and the schema define MANUAL `wheel` (a wheel speed setpoint) and `rate` (a box rate setpoint). The supervisor already implements everything around them: entry from READY with `input not available` refusal, the setpoint clamps (`wheel_rpm` to [Ω_low, Ω_cap], `rate_dps` to ±90), the 20 Hz limit, the 250 ms staleness rule (`rate` falls to 0, `wheel` holds) and the `MANUAL_STALE` flag. What is missing is the controller: `CascadeController` sends MANUAL to the open-loop throttle for every input, and `control_task.cpp` builds only `kRungOneBuiltInputs` (throttle), so both inputs answer `input not available`.

**Approach.**
1. **Controller** (`control.cpp`), when `wheel_loop_available(params)` (Hall fitted and the T-5 table set), MANUAL no longer leaves the closed loop for `wheel` and `rate`:
   - `rate`: the same path as READY: the rate loop runs with `demand.omega_cmd_dps = demand.manual_rate_dps`, driving ω_ref, and the wheel PI + feed-forward tracks it. Staleness is already in the supervisor (`manual_rate_dps` is 0 when stale).
   - `wheel`: the wheel loop alone, with the rate loop stopped (`stop_rate_loop()`, as in a bench wheel hold): ω_ref moves toward `demand.manual_wheel_rpm` at most `kWheelRefRampRpmPerS` (400 rpm/s, the SPINUP slope), never by a step, so a setpoint change cannot throw the box. The wheel PI tracks ω_ref. The box is free to turn; the flag `MOMENTUM_*` and the interlocks apply as in READY.
   - Entry from MANUAL `throttle` or from READY is bumpless, by the same rule READY already uses (ω_ref at the measured speed, integrator preset to the last throttle minus the feed-forward). `MANUAL throttle` is unchanged and stays open loop.
   - ω_ref is clamped to [`omega_ref_floor_rpm`, the cap in force] in both inputs. The floor is Ω_low + 100 (V-52): a wheel held exactly at Ω_low trips `UNDERSPEED`. FD §13.5 says the `wheel` clamp is [Ω_low, Ω_cap]; this feature amends it to the controller's floor, written into FD §13.5 and logged as a decision. The supervisor's own clamp stays [Ω_low, Ω_cap] (it is the outer limit, and the controller's floor is the tighter one).
2. **Built inputs** (`control.hpp`): a pure `built_manual_inputs(const Params&)` returns throttle, wheel and rate when `wheel_loop_available(params)`, else throttle only. `control_task.cpp` uses it where it sets `in.built_inputs` (today `kRungOneBuiltInputs`). With the Hall bypassed or no table the answer stays `input not available`, exactly as now: nothing changes for rung 1.
3. **Mock.** `tools/mock-box.py` accepts `wheel` and `rate` only when its wheel loop is available (a `--uncharacterised` box refuses them with `input not available`), and its MANUAL wheel ramps the reference at 400 rpm/s.

**Not changed:** the wire contract (FD §13.5 and schema v1 already define both inputs), the heartbeat, the interlocks, the caps, the 250 ms rule, the Hall-bypass throttle-only behaviour. No parameter is added, so `param_version` stays 2.

## Tests

- [ ] Host (`test_controllers.cpp`): with the table set, `built_manual_inputs` is throttle|wheel|rate; with no table, or with the Hall bypassed, it is throttle only; a supervisor given those inputs accepts `mode MANUAL input wheel` and `input rate`, and refuses them with `input not available` otherwise.
- [ ] Host, MANUAL `wheel` (plant sim, `test_closed_loop.cpp`): from READY at the bias, a setpoint 800 rpm higher moves ω_ref at no more than 400 rpm/s (measured per tick), the wheel reaches within 2 % of it, and `tau_cmd_mNm` is 0 (the rate loop is off). A setpoint above the cap holds at the cap; one below the floor holds at the floor; `UNDERSPEED` and `OVERSPEED` never trip in these runs. The wheel holds its speed when the setpoint goes stale.
  - Positive control: mutant `manual_wheel_step` (ω_ref jumps to the setpoint) is caught by the 400 rpm/s check.
- [ ] Host, MANUAL `rate` (plant sim): with a 30 deg/s setpoint the box reaches 30 ± 3 deg/s within 2 s and holds it; with the setpoint stale for 250 ms it returns to under 5 deg/s; the sign matches the wire (a positive wire rate is clockwise, FD §2.3).
  - Positive control: mutant `manual_rate_ignored` (the controller uses ω_cmd = 0 in MANUAL) is caught: the box never reaches 30 deg/s.
- [ ] Host: entering MANUAL `wheel` or `rate` from READY and returning with `mode READY` changes the throttle by no more than a few units in the hand-over ticks (bumpless), and `estop`, `disarm`, and a lost heartbeat from MANUAL `wheel` and `rate` still give SAFE and the ramp-down.
- [ ] `tools/mock-box.py --selftest`: both inputs work on the prepared box, and a `--uncharacterised` box refuses them with `input not available`; falsifier: the previous mock accepts them on an uncharacterised box.
- [ ] `tools/host-test.sh --selftest`, `tools/check-all.sh`, and `tools/check-all.sh --firmware` (the firmware build with the `control_task.cpp` line) pass.
- [ ] Hardware, with Julian's explicit go before each motor-capable step: on the bench rig, MANUAL `wheel` steps 200 rpm up and down and the wheel follows within 2 % without tripping an interlock; on the turntable, MANUAL `rate` at +10 and -10 deg/s turns the box the right way (clockwise on the wire is clockwise seen from above).
- [ ] UI: after the above, `modes.ts` flips MANUAL wheel and rate from `pending` to `available` in a separate UI PR (Aaron).
