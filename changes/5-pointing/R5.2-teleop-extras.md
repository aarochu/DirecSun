# R5.2: MANUAL `wheel` and `rate`, and the status flags

**Status:** built, host-verified; hardware pending (with Julian present for any spin)
**Approval:** as R5.1
**Files:** `firmware/components/direcsun_core/{src/control.cpp,modes.cpp,include/direcsun/core/control.hpp,modes.hpp}`, `firmware/main/control_task.cpp`, `protocol/schema-v1.json`, `firmware/test/host/{test_pointing.cpp,test_modes.cpp}`

## Spec

**Problem:** FD §13.5 defines three MANUAL inputs. Only `throttle` (open loop) was built; `wheel` and `rate` were refused with `input not available`. The UI shows a wheel-speed and a rate slider, and has no way to tell why a mode is refused.

**Approach:**
- **Built inputs** are all three (`kAllBuiltInputs`). `wheel` and `rate` also need the closed wheel loop at run time (Hall fitted and `ff_table` set); without it the refusal is `input not available`, as before.
- **`wheel`**: Ω_ref follows the operator's speed at the spin-up ramp rate (400 rpm/s), clamped to [Ω_low + margin, cap in force]; entry starts at the measured speed, so it is not a step. Staleness holds the last value.
- **`rate`**: the operator's rate is ω_cmd for the rate loop (±90 deg/s); it falls to 0 after 250 ms without a setpoint, with `MANUAL_STALE`.
- **Status flags** (additive, stay v1): `FF_TABLE_MISSING` when the Hall is fitted and `ff_table` is not set; `RATE_GAIN_REDUCED` when `rate_gain_scale` < 1 (0.2 after any parameter reset).
- **`PARAMS_RESET` reaches clients.** It was posted at the first tick, when no client has spoken, and events reach only clients that have. It is now posted to each client the tick its first message is handled.
